# Lessons learned

## What worked

**Decide the architecture once, in writing, with reasons.** The agent proposed three
foundational decisions with the alternatives and trade-offs laid out, and the developer signed
them off before any code. Nothing built later had to be rewritten because of them. Asking for
a recommendation plus reasoning produced better results than asking for code.

**Phase gates.** "Do not start the next phase until this one passes every check" stopped
half-working systems from piling up. It also gave a natural point to play the game and adjust.

**Self-verification through the editor.** The largest single improvement. An agent that can
compile, run tests, play the scene and take a screenshot stops reporting things as done when
they are not.

**Pure logic in its own assembly.** Pulling arithmetic out of engine components made it
testable in milliseconds with no scene, and it made the engine-facing code thin enough to
review by eye.

**Fresh subagent per task, independent reviewer at the end.** The implementer cannot lean on
unstated context, and the reviewer has no stake in the implementation.

**A ledger with rulings.** When the plan and reality disagreed, the agent wrote one line: what
it decided, and what it costs if that turns out wrong. Reading those lines afterwards is the
fastest way to audit a feature.

**Telemetry for behaviour that is hard to watch.** For the AI opponent, a log of decisions
read at high time scale found problems that hours of normal play had not.

**Updating the plan to "as built".** The master plan stayed accurate because each phase's
section was rewritten after it shipped.

## What did not work, and the fix

| Problem | Fix |
|---|---|
| The agent went quiet for a long time on a large plan and it was unclear whether it was stuck. | Ask it to state what it will do next, then run the plan in phases with a report after each. |
| An AI-versus-AI comparison gave a misleading result because the two sides did not have the same capabilities. | Test each configuration alone against the same baseline. Write down why. |
| A setting changed through MCP kept reverting. | The game's own bootstrap was overwriting it each frame. Find the owner of the value and go through it. |
| The console was useless for long runs because routine lines buried the interesting ones. | Hook the log and write only the lines that matter to a file. |
| A plan said "commit" after each task but the workspace was not a git repository. | Note it once in the ledger as a ruling, skip the step, keep the ledger as the record. |
| A plan step said "listen to the result". | The agent cannot hear. It inspected state instead and left the listening check to the developer, stated plainly. |
| The agent recompiled while the developer was in play mode, which wiped the running match and flooded the log with errors. | Stop play mode before any recompile. Treat errors that appear right after a reload as suspect. |
| A fix was reported as done when it had only been compiled. | Require the report to separate "compiles", "tests pass" and "confirmed in the running game", and to list what was not covered. |
| A performance pass could have changed how the game looks. | "Report first, change nothing" and then approve fixes one at a time. |

## Unity-specific gotchas

- Code in the default assembly cannot be referenced from a test assembly definition. Tests
  for it go in an `Editor` folder.
- The MCP connection drops for a moment on every domain reload after a recompile. Check the
  recompile status and carry on.
- `eval` snippets run without `using` directives. Fully qualify every type.
- Running tests from the command line fails while the editor has the project open. Use the
  Test Runner or the MCP call instead.
- New files need their `.meta` files generated by the editor before they are added to version
  control, or the metas are missed.
- The plain game view reports no safe-area insets. Use the device simulator for notch and
  home-indicator checks.
- Exclude generated build output and third-party folders from any code index.

## What still needs a human

- How a control feels on a real phone.
- How anything sounds.
- Heat, battery and throttling on a device.
- Whether the game is fun.
- Every design decision.
